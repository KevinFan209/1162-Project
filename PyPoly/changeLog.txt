[2026-07-29] #22 全流程整合測試（無瀏覽器，以程式扮演兩位玩家跑完整局）
  方式：以 requests + socketio.Client 依前端實際送出的參數與順序，完整走過
        登入→建房→加入→開局→抓地圖→決定先後手→擲骰移動→冒險答題→購地→
        開合跳→換回合→結算→結果頁→離開登出。共 69 項斷言。
  結果：69 PASS / 0 FAIL，伺服器全程未拋例外。
  同時另跑邊界情境測試（斷線、重整、背景清理），發現下列問題（本輪未修）：

  【阻斷級】
  1. game.html:7355 定義了 startSyncLoop() 卻從未被呼叫 → 進遊戲後全程零心跳，
     後端 60 秒無心跳的背景清理會把玩家判定離線（實測 t=50s 即 is_online=0）。
     後果：管理員後台顯示遊玩中玩家為離線；重複登入防護失效（實測對局中可用
     同帳號再次登入成功）。lobby.html / WaitingRoom.html 皆有正確呼叫，可對照。
  2. 完全沒有斷線處理：main.py 無 sio disconnect handler，前端亦無「對手離線」
     監聽。玩家關分頁後仍留在 room['players']；決定先後手階段對手一斷線，
     handle_order_dice 永遠湊不滿 2 人 → 遊戲死鎖。另 triggerGameOver 只由
     players[1] 送結算，該玩家離線則整局永不產生結算資料。
  3. 殭屍房間永久累積：active_rooms 只有明確 leave/delete 才清除，無逾時回收。
     實測有房間在客戶端崩潰後以 status=gaming 存活整輪測試，新玩家加入回
     400「房間已滿」。大廳會逐漸堆滿進不去的滿員房。

  【中等】
  4. game.html:6443 用 myName === players[1] 判定大回合結束，但 players 是
     加入順序，finalizeGameStart 決定先後手時不重排該陣列 → 客人擲骰贏得先手時，
     房主的最後一回合會被吃掉，每局 50% 機率不公平。
  5. game.html:6506 的 settle payload 只送 {username, final_money, laps}，
     未送 jump_count → 結算報表的開合跳次數永遠是 0。
  6. profile.html 呼叫兩個不存在的 API（實測皆 404）：
     POST /auth/update-profile、POST /auth/send-otp-new-email。
  7. modal.html:199-203「25 回合」「30 回合」兩個 option 的 value 都誤植為 20。
  8. /rooms/create 未將房號正規化為大寫，但 verify/join/leave/kick/start 都有

[2026-07-29] #25 修正註冊重複 email 造成 500，以及錯誤訊息被誤顯示為「連線失敗」
  現象：用新帳號註冊時畫面顯示「⚠️ 連線失敗 / 伺服器連線失敗」，但既有帳號登入正常。
  追查：伺服器記錄顯示 POST /auth/register 連續回 500，例外為
        pymysql.err.IntegrityError (1062, "Duplicate entry 's112213070@ncnu.edu.tw'
        for key 'uq_users_email'")。與前端 POST 寫法無關，請求有正確送達。

  成因（兩層）：
    1. main.py 的 register 只檢查 username 是否重複，未檢查 email；
       但 models.User.email 有 unique=True 約束，填入已被使用的信箱時
       由 DB 丟出 IntegrityError，該例外未被接住 → FastAPI 回 500。
    2. FastAPI 未處理例外時回傳的 body 是純文字 "Internal Server Error"
       (content-type: text/plain)。login.html 的失敗分支直接 await res.json()，
       解析純文字時拋 SyntaxError，被外層 catch(err) 接走，
       於是顯示成「伺服器連線失敗」——訊息與真正原因完全無關。
       這會讓「任何 5xx」都偽裝成連線問題，後續除錯會一直被誤導。

  檔案：main.py
    - import 增加 from sqlalchemy.exc import IntegrityError。
    - register 新增 email 重複檢查，回 400「此信箱已被註冊」。
    - db.commit() 包 try/except IntegrityError → rollback 後回 400
      「帳號或信箱已被使用」（保險：兩個請求同時通過前置檢查時仍由唯一鍵擋下）。
  檔案：static/login.html（約 line 399）
    - const errData = await res.json();
      改為 await res.json().catch(() => ({}))，
      訊息改為 errData.detail || `伺服器錯誤 (${res.status})`，
      使非 JSON 的錯誤回應不再讓成功/失敗分支崩進 catch。

  驗證：python -m py_compile main.py 通過；重啟伺服器後從 HTTPS 隧道實測四種情境——
        重複 email → 400「此信箱已被註冊」（原本 500）
        重複 username → 400「ID 已被使用」
        全新帳號 → 200 註冊成功
        新帳號登入 → 200 正常簽發 JWT
  備註：s112213070@ncnu.edu.tw 等四組信箱已被既有學號帳號使用，
        建立新測試帳號時需改用其他信箱。

[2026-07-30] #33 修正 /start 會貼出當下連不上的網址（DNS 傳播空窗期）
  現象：在 Discord 執行 /start，bot 回覆的網址點下去是無效連結，
        但本機 http://localhost:8000 正常。

  追查：隧道其實建立成功（cloudflared 記錄顯示 Registered tunnel connection），
    網址也正確。問題在 DNS 傳播的空窗期——
      - 向 Cloudflare DNS(1.1.1.1) 查詢：有 A 記錄 104.16.231.132。
      - 向本機 DNS(192.168.137.1，Windows 行動熱點的轉發器) 查詢：
        當下只回 AAAA(IPv6)，尚未回 A(IPv4)。
      - 而該主機的 IPv6 對外完全不通（實測連 cloudflare.com 也失敗）。
    → 瀏覽器拿到 IPv6 位址、連不上，顯示無效連結。
    數分鐘後同一網址即恢復正常（本機 DNS 也開始回 A 記錄），
    證實是傳播時間差而非設定錯誤。cloudflared 自己的橫幅亦提示
    "it may take some time to be reachable"。
    先前幾次測試沒事，只是點擊時 A 記錄已傳播完成——屬間歇性問題。

  根因（本專案的實作缺陷）：
    tunnel_manager.start() 取得網址後會呼叫 _wait_reachable() 驗證，
    但該函式的回傳值從未被接收，逾時也被當成無事發生。
    於是 bot「明知連不上」仍照樣把網址貼出來，且沒有任何提示。

  檔案：ops/services/tunnel_manager.py
    - _wait_reachable() 逾時由 30 秒放寬為 90 秒（30 秒對 quick tunnel 偏短）。
    - 新增模組狀態 _verified 與查詢函式 url_verified()，記錄上次驗證結果。
    - start() 改為 _verified = await _wait_reachable(...)，不再丟棄回傳值。

  檔案：ops/cogs/ops_cog.py
    - _bring_up() 依 url_verified() 調整回覆：
      驗證通過→綠色卡片（同以往）；
      驗證失敗→橙色卡片，仍貼出網址（對 DNS 已更新的組員往往可用），
      並附「⚠️ 尚未驗證連線」欄位說明原因與處置
      （等 1~2 分鐘、或請他人先試）。
      顏色差異讓使用者一眼判斷是否需要多等。

  驗證：針對新邏輯 9 項測試通過，含以注入假狀態模擬「驗證失敗」，
        確認警告欄位會出現、網址仍會貼出、顏色由綠轉橙、
        警告文字含原因與處置方式；
        另跑 services 層 22 項回歸測試全數通過（含端到端從隧道打回
        login.html 與 socket.io 皆 200）。bot 重啟後 6 個指令正常同步。
